# 버퍼 복사 시 널 종료 자리를 항상 남겨두기

**Lv1 / C 기초**

**프로젝트에서** `src/string/ft_string_bounds.c`의 `ft_strlcpy()`가 `capacity`까지 채우지 않고 항상 한 칸을 비워둔다.

```c
size_t ft_strlcpy(char *dest, const char *src, size_t capacity) {
    ...
    while (src[idx] != '\0' && idx + 1 < capacity) { // capacity가 아니라 capacity - 1까지
        dest[idx] = src[idx];
        ++idx;
    }
    dest[idx] = '\0';
    return (src_length);
}
```

**일반적으로** C 문자열은 실제 데이터 끝에 `'\0'`(널 종료 문자) 한 바이트가 반드시 있어야 "문자열 함수들이 어디서 멈춰야 하는지" 알 수 있다. 버퍼 크기(`capacity`)를 넘겨받아 그 안에서 복사하는 함수를 짤 때, 이 널 종료 문자를 쓸 자리를 계산에서 빼먹으면 두 가지 문제가 겹친다.

1. `capacity`바이트를 데이터로 꽉 채우면 종료 문자를 쓸 자리가 없어 그다음 바이트(버퍼 밖)에 쓰게 되는 오버런.   

2. 설령 오버런이 안 나도 문자열이 끝나지 않아 뒤에 이어지는 임의의 메모리 내용을 계속 "문자열의 일부"로 잘못 읽게 된다.

그래서 **"복사 가능한 바이트 수 = capacity - 1"**이라는 계산이 이런 함수들의 핵심 불변식이다.

**모범사례**:  
표준 `strcpy`(용량 제한 없음)와 `strncpy`(용량은 받지만 널 종료를 보장하지 않는 경우가 있음)가 실무에서 반복적으로 버퍼 오버플로 취약점의 원인이 됐던 이유가 바로 이 계약의 모호함이다. BSD가 제안한 `strlcpy`/`strlcat`(이 프로젝트가 재구현한 버전)은 "항상 널 종료를 보장하고, 반환값으로 잘렸는지 여부를 알려준다"는 더 명확한 계약으로 이 문제를 해소한다. 다만 표준 C 라이브러리에는 아직 포함되지 않아(POSIX 표준이 아님), 이식성이 필요한 코드에서는 여전히 직접 구현하거나 대체 함수(`snprintf` 활용 등)를 쓰는 경우가 많다.
