# 시그널 핸들러 안에서 부를 수 있는 함수가 제한되는 이유

**Lv1 / 시스템**

**프로젝트에서** `src/server.c`의 시그널 핸들러(`handle_bit`)가 리팩터 이후 `write()` 하나만 부르고 끝난다. 그 전 버전은 핸들러 안에서 전역 변수를 갱신하고 값을 조립하는 일반 코드를 실행했다.

```c
static void	handle_bit(int signal, siginfo_t *info, void *context)
{
    ...
    if (MT_EVENT_WRITE(g_event_pipe[1], &event, sizeof(event))
        != (ssize_t)sizeof(event))
        g_event_overflow = 1;
    errno = saved_errno;
}
```

**일반적으로** 시그널은 프로그램 실행 중 "지금 실행하던 코드 흐름을 강제로 멈추고" 끼어든다. 그 시점이 언제일지(어떤 함수 안, 어떤 락을 잡고 있는 도중 등)는 예측할 수 없다. 만약 원래 실행 중이던 코드가 `malloc()` 내부에서 힙 관리 자료구조를 갱신하는 도중이었는데, 핸들러가 끼어들어 또 `malloc()`을 부르면 그 자료구조가 일관되지 않은 상태에서 재진입하게 되어 힙이 깨질 수 있다. 이런 이유로 POSIX는 시그널 핸들러 안에서 호출해도 안전하다고 보장하는 아주 좁은 함수 목록(async-signal-safe 함수)을 정해뒀다(`write()`, `read()`, `_exit()` 등 극히 기본적인 시스템 콜 몇 개뿐이고, `malloc()`, `printf()`, 대부분의 표준 라이브러리 함수는 이 목록에 없다).

**모범사례**:  
이 제약을 지키는 실무적인 해법이 바로 이 프로젝트가 쓰는 패턴이다. 핸들러는 "지금 일어난 일"을 최소한의 정보로 안전한 방법(파이프에 쓰기, 또는 `volatile sig_atomic_t` 전역 플래그 하나를 세팅)으로만 기록하고, 실제 처리는 시그널 컨텍스트를 벗어난 평범한 코드(메인 루프)에서 한다. 반대로 "일단 되니까"라는 이유로 핸들러 안에서 `malloc`/`printf` 같은 함수를 부르는 코드는, 대부분의 실행에서는 문제없이 동작하다가 아주 드문 타이밍(하필 그 함수 내부에서 인터럽트된 경우)에만 죽어서, 재현하기 매우 어려운 버그가 된다.
