# 블랙박스 CLI 테스트와 화이트박스 API 테스트의 차이

**Lv1 / 테스트**

**프로젝트에서** `tests/smoke.sh`(및 `faults.sh`/`allocation.sh`/`lifecycle.sh`)는 컴파일된 `./small-shell` 실행 파일을 실제로 fork/exec해서 표준 입력에 명령을 흘려보내고 표준 출력·종료 코드만 검사한다. 셸 내부 함수를 전혀 모른 채 "밖에서 보이는 동작"만 검증하는 블랙박스 방식이다. 반대로 `tests/parser_api.c`는 `shell.h`가 선언한 `shell_parse_line()` 같은 내부 함수를 테스트 코드가 직접 `#include`하고 링크해서 호출한다. 실행 파일을 거치지 않고 함수 하나를 그 반환값·출력 매개변수까지 직접 검사하는 화이트박스 방식이다.

**일반적으로** 블랙박스 테스트는 "사용자가 실제로 보는 동작"을 보장하고 구현이 바뀌어도(리팩터링) 잘 안 깨진다는 장점이 있지만, 에러 메시지 포인터가 `NULL`일 때만 발생하는 것 같은 세밀한 내부 분기(devlog 01의 `error == NULL` 버그)는 CLI 출력만으로는 재현하거나 구분하기 어려울 수 있다. 화이트박스 테스트는 그런 내부 분기를 직접 겨냥할 수 있지만, 내부 함수 시그니처가 리팩터링되면 테스트 코드도 같이 손봐야 해서 구현에 더 강하게 결합된다.

**모범사례**:  
이 프로젝트는 두 방식을 상호 배타적으로 고르지 않고 계층별로 나눠 썼다. 대부분의 회귀는 블랙박스(`smoke.sh`류)로 충분히 잡히고, 공개 API의 세밀한 계약(에러 포인터가 `NULL`일 때의 동작)처럼 CLI 출력만으로는 구분하기 어려운 지점만 화이트박스(`parser_api.c`)로 별도로 짚었다. 실무에서도 이 조합(E2E/통합 테스트는 블랙박스, 유닛 테스트는 화이트박스)이 흔한 기본 전략이다.
