# self-pipe 트릭으로 시그널을 이벤트 루프 안전하게 흘려보내기

**Lv2-core / 시스템**

**프로젝트에서** `src/server.c`가 시그널 핸들러 안에서 이벤트를 파이프에 써넣고(`write(g_event_pipe[1], &event, sizeof(event))`), 메인 루프가 그 파이프를 `select`/`read`로 기다렸다가 실제 처리를 한다. 이벤트 구조체 크기가 `PIPE_BUF`(파이프 쓰기가 원자적으로 보장되는 최대 크기) 이하인지를 컴파일 타임에 강제한다.

```c
typedef char t_event_must_fit_pipe_buf[(sizeof(t_bit_event) <= PIPE_BUF) * 2 - 1];
```

**일반적으로** 시그널 핸들러는 극히 제한된 함수만 안전하게 부를 수 있다는 게 앞선 문서의 요지였다. 그런데 실제 프로그램은 "시그널이 왔다"는 사실을 계기로 훨씬 복잡한 일(이 프로젝트라면 비트 조립, ACK 전송)을 해야 한다. self-pipe 트릭은 이 둘을 분리한다. 파이프 하나를 만들어두고, 시그널 핸들러는 그 파이프에 "무슨 일이 일어났는지"를 나타내는 작은 데이터만 `write()`한다(async-signal-safe). 프로그램의 나머지 부분(이벤트 루프)은 평소처럼 `select`/`poll`/`epoll`로 그 파이프의 읽기 쪽을 다른 모든 입출력과 동등하게 감시하다가, 데이터가 도착하면 그때 안전하게 실제 처리를 한다. 시그널이라는 비동기적 사건을, 이벤트 루프가 원래 다루는 동기적인 "파이프에 데이터가 도착함" 이벤트로 바꿔치기하는 것이다.

`PIPE_BUF` 이하 크기의 쓰기가 원자적이라는 보장(POSIX)이 이 트릭의 핵심 전제다. 여러 시그널이 짧은 시간에 연달아 와서 핸들러가 여러 번 겹쳐 실행되더라도, 각 `write()` 호출이 서로 뒤섞이지 않고 통째로 파이프에 들어간다는 보장이 없으면 이벤트 구조체가 반쪽씩 섞여 읽힐 수 있다. 이 프로젝트가 그 크기를 컴파일 타임 assert로 강제해둔 이유가 이것이다.

**모범사례**:  
이 트릭은 Linux 전용 `signalfd(2)`가 나오기 전까지 시그널을 이벤트 루프에 통합하는 사실상 유일한 이식성 있는 방법이었다. `signalfd`는 시그널 자체를 파일 디스크립터로 노출해줘서 별도 파이프와 핸들러 없이 `read()`로 시그널 정보를 직접 받을 수 있게 해준다. 다만 Linux 전용이라, macOS를 포함한 이식성이 필요한 코드에서는 여전히 self-pipe 트릭이 표준적인 선택이다.
