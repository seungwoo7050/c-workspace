# 해제 전에 다음 포인터를 먼저 저장해 use-after-free 막기

**Lv2-core / 메모리 안전성**

**프로젝트에서** `src/list/ft_list_lifecycle.c`의 `ft_lstclear()`가 노드를 순회하며 전부 해제할 때, 매 반복마다 `next`를 먼저 지역 변수에 저장한 뒤에야 현재 노드를 해제한다.

```c
void ft_lstclear(t_list **list, void (*del)(void *)) {
    t_list *next;

    while (*list != NULL) {
        next = (*list)->next;     // 1) 먼저 읽는다
        ft_lstdelone(*list, del); // 2) 그다음 해제한다
        *list = next;             // 3) 저장해둔 값으로 이동한다
    }
}
```

**일반적으로** 연결 리스트를 순회하며 해제할 때, "지금 노드를 해제 → 그 노드의 `next`를 읽어서 다음으로 이동"하는 순서로 짜면 두 번째 단계가 이미 `free()`된 메모리를 읽는 use-after-free가 된다. C의 `free()`는 그 메모리를 즉시 물리적으로 지우거나 접근 불가능하게 만들지 않는다. 할당자에게 "이 블록은 재사용해도 된다"고 알릴 뿐이라, 해제 직후 같은 값을 읽으면 우연히 이전 값 그대로 보이는 경우가 많다(그래서 이런 버그가 로컬 테스트에서는 안 걸리다가 다른 환경/시점에 터진다). **안전한 순서는 항상 "해제 대상이 갖고 있는, 다음에 필요한 값을 먼저 꺼내고 나서 해제한다"이다.**

**모범사례**:  
이 문제는 개별 코드 리뷰로 잡을 수도 있지만, 근본적으로는 AddressSanitizer 같은 도구가 계측된 빌드에서 실제로 그 메모리에 접근하는 순간 프로그램을 멈춰 세워 정확한 위치를 알려주는 방식으로 훨씬 신뢰성 있게 잡힌다(포인터 값이 우연히 유효해 보이면 리뷰만으로는 놓치기 쉽다). 실무에서 연결 자료구조를 순회하며 해제하는 코드를 짤 때는, 이 순서 원칙을 습관화하는 동시에 sanitizer 계측 빌드로 한 번은 실제로 돌려보는 것이 표준적인 이중 안전장치다.
