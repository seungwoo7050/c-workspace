# 기수 정렬 전에 값을 조밀한 상대 순위로 바꿔야 하는 이유

**Lv2-core / 알고리즘**

**프로젝트에서** `src/sort.c`의 `radix_sort()`가 원래 입력값이 아니라 `a->ranks[0]`(입력 전체에서 몇 번째로 작은 값인지, 0부터 `size - 1`까지의 상대 순위)의 비트를 검사한다.

```c
bits = count_bits(a->size);   // size개를 구분하는 데 필요한 최소 비트 수
...
if (((a->ranks[0] >> bit) & 1) == 1)
    op_ra(a, 1);
```

**일반적으로** 기수 정렬은 값을 자릿수(또는 비트) 단위로 훑으며 통 정렬(bucket sort)을 반복하는 방식인데, 이때 필요한 라운드 수는 "값을 표현하는 데 필요한 자릿수/비트 수"에 비례한다. 원래 입력값을 그대로 쓰면, 예를 들어 입력이 `{1, 1000000000}` 두 개뿐이어도 `1000000000`을 표현하려면 30비트 가까이 필요해서 라운드 수가 쓸데없이 많아진다. 원소 개수(2개)에 비해 훨씬 비효율적이다. 반면 "이 값이 전체에서 몇 번째로 작은가"라는 순위로 바꾸면, `n`개의 원소는 항상 `0`부터 `n-1`까지의 순위를 갖고, 그 범위를 표현하는 데 필요한 비트 수는 $log2(n)$으로 원소 개수에만 비례한다. 원래 값이 아무리 크거나 희소해도 정렬에 필요한 라운드 수는 항상 입력 크기만으로 결정된다.

**모범사례**:  
이 변환(값 → 조밀한 순위)은 "정렬해야 할 값의 범위가 넓거나 예측 불가능할 때, 기수 정렬 같은 범위 의존적 알고리즘을 쓰기 전에 그 범위를 원소 개수만큼으로 좁힌다"는 일반적인 전처리 기법이다. 실무에서도 좌표 압축(coordinate compression)이라는 이름으로 같은 기법이 쓰인다. 예를 들어 아주 큰 좌표 범위를 다루는 세그먼트 트리를 만들 때, 실제 등장하는 좌표값만 순위로 압축해서 트리 크기를 원소 개수에 비례하게 만드는 것과 동일한 발상이다.
