# Dev Log 01. Sorting with only rotate and push: why radix sort fits

## 1. `feat(sort): 큰 입력을 기수 정렬로 처리`

```c
static void radix_sort(t_stack *a, t_stack *b)
{
    bits = count_bits(a->size); // size개를 구분하는 데 필요한 최소 비트 수
    bit = 0;
    while (bit < bits) {
        i = 0;
        while (i < round_size) {
            if (((a->ranks[0] >> bit) & 1) == 1)
                op_ra(a, 1); // 이 비트가 1이면 뒤로 순환
            else
                op_pb(a, b, 1); // 0이면 b로 옮겨 그 순번대로 쌓음
            i++;
        }
        while (b->size > 0)
            op_pa(a, b, 1); // b에 쌓인 걸 다시 a로 (역순으로 쌓였던 게 복구됨)
        bit++;
    }
}
```

이 셸에서 쓸 수 있는 연산은 스택 맨 위 원소를 옮기거나(`push`), 회전(`rotate`)하거나, 맞바꾸는(`swap`) 것뿐이다. 인덱스로 중간 원소에 직접 접근할 방법이 없다. 이런 제약 안에서 값 하나하나를 비교하는 정렬(퀵정렬, 병합정렬 등)은 원소 접근 자체가 회전을 반복해야 해서 비효율적이다. 기수 정렬(radix sort)은 "값을 직접 비교"하는 대신 "각 값을 나타내는 비트를 최하위(또는 여기서는 상대순위의 최상위)부터 한 자리씩 훑으며, 그 자리 비트가 0인지 1인지로 두 무더기(스택 a/스택 b)로 나누는" 방식이라 "지금 맨 위 원소의 비트가 뭔지 확인하고 그에 따라 옮긴다"는 동작이 이 셸의 연산(맨 위만 접근 가능)과 정확히 맞아떨어진다.

`a->ranks[0]`은 원래 값이 아니라 "이 값이 전체 입력에서 몇 번째로 작은가"라는 상대 순위(0부터 size-1까지의 밀집된 정수)다. `count_bits(size)`가 "size개를 구분하는 데 필요한 비트 수"를 정확히 계산할 수 있는 건, 원래 입력값이 임의로 크거나 희소할 수 있는 반면 순위는 항상 `0`~`size-1`로 조밀하기 때문이다. 원래 값을 그대로 썼다면 필요한 비트 수가 값의 크기에 따라 임의로 커질 수 있었다.

## 정리

"가진 연산이 맨 위 원소 접근뿐"이라는 제약이 알고리즘 선택 자체를 결정한다는 게 이 과제의 핵심이다. 일반적인 상황에서 최선인 정렬 알고리즘(퀵정렬 등)이 이 제약 안에서는 최선이 아닐 수 있고, 반대로 잘 안 쓰이는 알고리즘(기수 정렬)이 이 구조에 딱 맞을 수 있다. "어떤 연산이 허용되는가"가 "어떤 알고리즘이 적절한가"를 바꾼다.
