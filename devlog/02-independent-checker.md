# Dev Log 02. The checker never trusts push_swap's own logic

## 1. `feat(checker): 명령 실행 결과를 판정`

```c
// main의 이 시그니처는 프로그램 실행 시 커맨드라인 인자를 받는 표준 형태다
// argc: 인자 개수(프로그램 이름 포함), argv: 각 인자를 문자열로 담은 배열(argv[0]이 프로그램 이름)
int main(int argc, char **argv)
{
    parse_input(argc, argv, &a); // push_swap과 같은 원본 입력을 다시 받는다
    stack_init(&b, a.capacity);
    read_and_apply(&a, &b); // push_swap이 출력한 명령을 표준 입력에서 읽어 그대로 재실행
    if (stack_is_complete_sorted(&a, &b))
        ps_putstr_fd(1, "OK\n");
    else
        ps_putstr_fd(1, "KO\n");
}
```

`checker`는 `push_swap`이 만든 정렬 명령이 실제로 입력을 정렬하는지 검증하는 별도 실행 파일이다. 핵심은 이 프로그램이 `push_swap`의 정렬 로직(기수 정렬 등)을 전혀 공유하지 않는다는 것이다. 같은 원본 입력을 독립적으로 다시 받아, `push_swap`이 표준 출력으로 내놓은 명령들을 한 줄씩 그대로 재실행하고, 그 결과가 실제로 정렬됐는지(그리고 스택 b가 완전히 비었는지)만 확인한다.

## 정리

"결과를 만든 코드와 그 결과를 검증하는 코드가 같은 로직을 공유하면, 그 로직에 있는 버그를 검증 코드도 똑같이 못 잡는다"는 게 이 설계의 핵심이다. `push_swap`의 기수 정렬 구현에 버그가 있어서 항상 마지막 원소 하나를 빠뜨린다고 해보자. 만약 `checker`가 `push_swap`과 같은 정렬 함수를 재사용해서 "정답"을 계산했다면, 그 정답도 똑같이 마지막 원소가 빠진 채로 계산되어 버그가 있는 출력과 우연히 일치하고 통과해버릴 수 있다. `checker`가 순수하게 "명령을 그대로 실행했을 때 실제로 정렬된 상태가 되는가"만 독립적으로 재확인하기 때문에, `push_swap` 쪽의 알고리즘이 무엇이든, 그 구현에 어떤 버그가 있든 상관없이 결과만으로 정확하게 판정할 수 있다. 이건 실무의 "구현과 검증을 분리하라"는 원칙의 가장 단순한 형태다. 테스트가 프로덕션 코드와 같은 실수를 공유하지 않게 하려면, 검증 로직 자체가 프로덕션 로직에 최대한 의존하지 않아야 한다.
